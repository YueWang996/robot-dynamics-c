# 约定 {#conventions}

这一页列的每件事，弄错了都不会报错。程序照常跑完，返回 `RD_OK`，给你一组看着挺
合理的数字，而机器人是错的。运行时也查不出来——一个顺序装反的四元数，模长仍然是 1。

好消息是这些约定和 [Pinocchio](https://github.com/stack-of-tasks/pinocchio)、
[bard](https://github.com/YueWang996/bard-pytorch-dynamics) 完全一致。你为那两个写的
`q` 向量可以直接喂给这个库，反过来也行。

## 一页速查

| | |
|---|---|
| 基座位姿 | `q_base = [x y z qw qx qy qz]`，**标量 qw 在前** |
| 基座速度、加速度 | 表达在根连杆的**体坐标系**里 |
| 空间向量 | `[线量三维, 角量三维]`，线量在前 |
| `qd`、`qdd`、`tau` | 长度都是 `nv`，基座占前六位 |
| `M` | `nv × nv`，上下三角都填满 |
| 关节顺序 | 按 URDF 里声明的顺序做深度优先遍历 |
| 重力 | 传 `NULL` 等于世界系下的 `{0, 0, -9.81}` |

## 位形分两个参数传，速度只有一个

浮动基座的机器人，位形的维数和速度的维数不相等。原因是姿态：三个转动自由度用四元数
表示要四个数。所以位形是 `nq` 维、速度是 `nv` 维，`nq = nv + 1`。

库把位形拆成两个参数传，省得你自己去数偏移量：

```c
rd_real_t q_base[7];         /* x y z qw qx qy qz —— 前三个位置，后四个姿态四元数 */
rd_real_t q_joints[nj];      /* 每个驱动关节一个角度或位移                       */
rd_real_t qd[nv];            /* 浮动基座 nv = 6 + nj；固定基座 nv = nj           */
```

固定基座的机器人给 `q_base` 传 `NULL`，基座就摆在原点、姿态为单位四元数。
`q_joints` 传 `NULL` 是全零位形，`qd` 传 `NULL` 是静止。

四元数的标量在前，这一条最值得复核。ROS 和 Eigen 写的都是 `[x y z w]`，标量在后。
把一个 `[x y z w]` 的四元数直接塞进 `q_base[3..6]`，它的模长还是 1，所有检查都过，
你得到的是一个姿态莫名其妙的机器人。

## 基座速度在根连杆自己的坐标系里

`qd[0..5]` 是基座的空间速度，表达在**根连杆自己的坐标系**里。这是 Pinocchio 的
free-flyer 约定。它不是"基座原点在世界系下的速度"，这两个差一个旋转。

状态估计器给你的通常是世界系的速度旋量。放进 `qd` 之前先把它转到根坐标系。

`qdd[0..5]` 同理。`tau[0..5]` 也在这个系里，它的含义是作用在基座上的合力旋量。
浮动基座没有电机，所以这六行里剩下的东西，是你给的那组力矩没能满足的平衡条件。
@ref contacts "接触与闭链" 里有一个具体例子说明这个残差怎么变成机器人的运动。

## 空间向量是线量在前

刚体动力学里六维的量（速度、加速度、力）叫空间向量。这个库里线量占前三位：

```
v = [vx vy vz  wx wy wz]        速度：前三个平动，后三个转动
f = [fx fy fz  tx ty tz]        力：  前三个力，  后三个力矩
```

雅可比的六行也是这个顺序：前三行对应线速度，后三行对应角速度。

Featherstone 的书里角量在前，跟这里相反。抄书上的公式时留意一下。

## 「世界系」到底指什么

rd_frame_t 有两个取值，会被误解的是 RD_FRAME_WORLD。

- `RD_FRAME_LOCAL` —— 结果表达在这个 frame 自己的坐标轴上，取在它自己的原点。
- `RD_FRAME_WORLD` —— 对应 Pinocchio 的 `ReferenceFrame.WORLD`：坐标轴用世界系的，
  但**取矩点在世界原点**。

要小心的是 `RD_FRAME_WORLD` 和 `LOCAL_WORLD_ALIGNED` 是两个东西。后者也用世界系的
坐标轴，但取矩点在 frame 自己的原点上。多数人想要的其实是 LOCAL_WORLD_ALIGNED ——
"这只脚在世界系里往哪个方向动、动多快"。

两者只有在 frame 原点正好压在世界原点上时才相等。差的那一项随距离增长，所以这个错误
在小机械臂上表现为不起眼的小误差，在腿上就是大误差。

自己转换一下就有了。把 WORLD 的结果平移到点 `p`：

```c
rd_jacobian(&chain, &state, frame, RD_FRAME_WORLD, J);
/* J 是行主序的 6 x nv。把线速度那三行平移到点 p 上： */
for (int c = 0; c < nv; ++c) {
    rd_real_t wx = J[3*nv + c], wy = J[4*nv + c], wz = J[5*nv + c];
    J[0*nv + c] -= p[1]*wz - p[2]*wy;
    J[1*nv + c] -= p[2]*wx - p[0]*wz;
    J[2*nv + c] -= p[0]*wy - p[1]*wx;
}
```

加速度还要再多一项。一个点的经典加速度等于平移过去的空间加速度再加上 ω × ṗ。
rd_spatial_acceleration() 返回的是空间加速度，那个叉乘项你自己补。

## RD_ANCHOR_WORLD 和 RD_FRAME_WORLD 是两码事

名字长得像，含义毫无关系，而且编译器分不出来。

| | 类型 | 值 | 含义 |
|---|---|---|---|
| RD_FRAME_WORLD | rd_frame_t | 0 | 结果表达在哪个系里 |
| RD_ANCHOR_WORLD | rd_idx_t | -1 | 约束的另一端接的是世界（地面） |

给约束的 `frame_b` 填 RD_FRAME_WORLD 能编译通过，因为它是个值为 0 的枚举，当索引用
就是"0 号连杆"，也就是基座。结果是你把脚约束到了机身上：脚跟着身体一起动，求解返回
的数字看起来还挺正常。

## 关节顺序

按 URDF 里声明关节的顺序做深度优先遍历，和 Pinocchio 一致。`tools/urdf2c.py` 转换时
会把完整的映射表打出来。运行时用 rd_chain_find_frame() 按名字拿索引，别硬编码数字。

固定连杆占一个 frame 索引，但不占速度索引。脚通常就是固定连杆：它有索引，可以对它求
雅可比、可以在它上面加约束，但它对 `nv` 没有贡献。

## 质量矩阵是填满的

rd_crba() 把 `nv × nv` 的上下三角都写满，行主序。可以直接传给 rd_cholesky_factor()，
后者只读下三角，不介意上面有东西。

## 单位

全程 SI。米、弧度、千克、牛顿、牛·米、秒。惯量是 kg·m²。armature（折算转子惯量）的
单位跟 `M` 的对角元一致，转动关节下也是 kg·m²。
