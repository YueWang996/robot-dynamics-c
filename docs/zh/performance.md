# 性能 {#performance}

这一页所有数字都是在写明的那块板子上实际跑出来的。原始 CSV 在 `benchmark/results/`
下，`tools/report.py` 从它生成这些表。

## Go2 上每个函数要多久

Go2 是宇树的四足机器人：18 自由度，31 个连杆，浮动基座。下面是单次调用的微秒数，
单精度，`-O3`。

| | **M4F @ 170**<br><sub>STM32G474</sub> | **M4F @ 80**<br><sub>STM32L413</sub> | **M33 @ 150**<br><sub>RP2350</sub> | **Hazard3 @ 150**<br><sub>RP2350</sub> | **RV32 @ 160**<br><sub>ESP32-C6</sub> |
|---|---|---|---|---|---|
| | 有 FPU | 有 FPU | 有 FPU | *无 FPU* | *无 FPU* |
| `update_kinematics` | 26.9 | 55.5 | 24.9 | 265.3 | 354.7 |
| `fk_frame` | 10.7 | 22.2 | 9.9 | 107.0 | 142.1 |
| `jacobian_world` | 12.2 | 25.4 | 10.3 | 63.8 | 81.0 |
| `jacobian_local` | 19.9 | 41.4 | 16.7 | 177.6 | 224.2 |
| `rnea` | 44.1 | 93.3 | 45.4 | 767.9 | 938.4 |
| `crba` | 54.7 | 113.4 | 55.9 | 530.4 | 678.9 |
| `aba` | 157.5 | 326.9 | 120.2 | 1756.8 | 2211.9 |
| `gravity` | 33.1 | 67.9 | 32.7 | 314.3 | 471.5 |
| `spatial_acceleration` | 19.4 | 40.6 | 17.9 | 202.8 | 275.6 |
| `spatial_velocity` | 4.7 | 9.7 | 4.6 | 52.3 | 72.5 |
| | | | | | |
| **力矩周期** | 71 µs<br>14.1 kHz | 149 µs<br>6.7 kHz | 70 µs<br>14.2 kHz | 1033 µs<br>968 Hz | 1293 µs<br>773 Hz |
| **操作空间** | 126 µs<br>8.0 kHz | 262 µs<br>3.8 kHz | 126 µs<br>7.9 kHz | 1564 µs<br>640 Hz | 1972 µs<br>507 Hz |
| **正动力学** | 184 µs<br>5.4 kHz | 382 µs<br>2.6 kHz | 145 µs<br>6.9 kHz | 2022 µs<br>495 Hz | 2567 µs<br>390 Hz |

最后三行是把单个函数拼成实际用途之后的总时间和对应的最高控制频率：

- **力矩周期**：`update_kinematics` + `rnea`。做力矩控制或者重力补偿，这就是你每个
  周期要付的钱。
- **操作空间**：再加一个 `crba`。任务空间控制器需要质量矩阵。
- **正动力学**：`update_kinematics` 加上 ABA 和 CRBA 里对这台机器人更快的那个。
  做仿真用。

@note G474、L413、ESP32-C6 三列是当前版本测的。两列 RP2350 是上一个版本采集的，
它们的 `rnea` 和 `gravity` 会偏慢几个百分点，因为那次改动只在有 FPU 的核上有效果，
在 Hazard3 上一分钱都不值。另外 Pico 2 的镜像是唯一按 `copy_to_ram` 链接的，代码在
RAM 里跑，不付 flash 等待周期——150 MHz 的 M33 能追平 170 MHz 的 M4F，主要就是这个
原因。

## 换个机器人会怎样

同一块 STM32G474 @ 170 MHz，换四个不同规模的模型：

| 机器人 | nv | 力矩周期 | 操作空间 | 正动力学 |
|---|---|---|---|---|
| `spine` | 9，浮动 | 26 µs — 38.0 kHz | 44 µs — 22.8 kHz | 59 µs — 16.9 kHz |
| `xarm7` | 7，固定 | 46 µs — 21.9 kHz | 84 µs — 11.8 kHz | 95 µs — 10.5 kHz |
| `go2` | 18，浮动 | 71 µs — 14.1 kHz | 126 µs — 8.0 kHz | 184 µs — 5.4 kHz |
| `g1` | 35，浮动 | 157 µs — 6.4 kHz | 353 µs — 2.8 kHz | 437 µs — 2.3 kHz |

`g1` 是宇树 G1，29 自由度的人形机器人，40 个连杆，浮动基座，是这套测试里最大的模型。
它在一颗 Cortex-M4F 上能闭 6 kHz 的力矩环；换到 80 MHz 的 L413 上是 3 kHz，
占用 64 KB 以内的 RAM。

## 正动力学该选 ABA 还是 CRBA

两个算出来的结果一样，快慢看机器人。下表是 `update_kinematics` 加上各自方法的总时间，
在两块 Cortex-M4F 上测的结果一致到一个百分点以内，所以这是机器人的性质，跟板子无关。

| 机器人 | nv | ABA | CRBA | 赢家 |
|---|---|---|---|---|
| `xarm7` | 7，固定 | 257 µs | **198 µs** | CRBA 快 23% |
| `spine` | 9，浮动 | **123 µs** | 128 µs | ABA 快 4% |
| `go2` | 18，浮动 | **382 µs** | 435 µs | ABA 快 12% |
| `g1` | 35，浮动 | **908 µs** | 1704 µs | ABA 快 47% |

（微秒数取自 L413 @ 80 MHz。）

有两个因素在拉扯，方向相反。

CRBA 要解一个 `nv × nv` 的方程组，Cholesky 分解的代价按 nv³ 涨，而且没有可以跳过的
部分。浮动基座让这件事更糟：基座那六个自由度是所有关节的祖先，会把质量矩阵填满，
稀疏性全没了。所以机器人越大、越是浮动基座，CRBA 越吃亏。

另一边，ABA 内部有一步关节体惯量的同余变换。当关节的安装偏置不带旋转时，这一步能走
一条便宜得多的路径。Go2 十二个关节全都满足，spine 三个也全满足。xarm7 的关节偏置是
四分之一转，一个都不满足，ABA 只能走通用路径——所以 nv 只有 7 的 xarm7 反而是 CRBA
唯一赢的模型。

spine 上那 4% 的差距，换个模型就可能翻过来，所以自己测。benchmark 里 `fd_crba` 那行
对 `aba` 那行，就是这个比较。

## 一定要选带硬件 FPU 的芯片

这组对比是在同一块 STM32L413 @ 80 MHz 上做的：把 benchmark 按 Cortex-M3 软浮点编译，
跑在同一块硅片上。时钟一样、flash 一样、源码一样，只有 `-mcpu` 和 `-mfloat-abi` 不同。

| | 没有 FPU 会慢多少 |
|---|---|
| `jacobian_world` | 6–10 倍 |
| `update_kinematics` | 7–12 倍 |
| `crba` | 7–16 倍 |
| `aba` | 12–13 倍 |
| `rnea` | **10–19 倍** |

倍数跟着算术密度走，浮点运算越密集的函数掉得越狠，所以 `rnea` 最惨。flash 会涨大约
16 KB，是软浮点例程加上膨胀的代码。RAM 不变，数据布局跟有没有 FPU 无关。

结论是：与其选一颗主频更高的标量核，不如选一颗带单精度 FPU 的。80 MHz 的 M4F 比
72 MHz 的 M3 快十倍以上。STM32 这边，F303 和 G431 在价格和引脚上都跟 F103 接近，
可以直接换。

## 占多少空间，最小能跑在什么芯片上

下面是开 `--gc-sections`、float32、只用 `update_kinematics + rnea + jacobian + crba
+ gravity` 这几个函数、16 连杆 12 关节的配置：

| | flash | RAM |
|---|---|---|
| M4F 硬浮点 | 23.5 KB | 6.8 KB |
| Cortex-M3 软浮点 | 39.6 KB | 6.8 KB |
| M3，`RD_ENABLE_ABA=0` | 39.6 KB | 5.2 KB |
| M0+ 软浮点 | 41.7 KB | 6.8 KB |

整个库是 40.2 KB 的 Cortex-M4 代码，上表的 23.5 KB 是链接器丢掉这个程序没调用的部分
之后剩下的。

Cortex-M0+ 能编译能链接，说明库里没有 ARMv7-M 或者 DSP 指令的依赖，`RD_USE_CMSIS_DSP`
默认也是关的。**它装得进 STM32F103C8**，64 KB flash、20 KB RAM。

按周期数折算到 72 MHz 的 F103，力矩周期大概是：2 自由度机械臂 2.5 kHz，spine 1.3 kHz，
xarm7 650 Hz，Go2 380 Hz，G1 160 Hz。这几个数偏乐观，因为 F103 只有预取缓冲、没有
指令缓存，而这个库是取指受限的。结论：重力补偿、慢速轨迹跟踪可以做；腿上的力矩控制
别指望。

## 跟代码生成比

Pinocchio 可以把 RNEA、ABA、CRBA 做符号化追踪，再让 CasADi 为某一台具体的机器人生成
直线 C 代码：没有循环，没有树遍历，所有公共子表达式都消掉了。这是能找到的最强对手，
所以 `benchmark/codegen/` 就是对着它测的。两边都是 float32、`-O3`、同一个编译器、
同一块板子，而且都对照 Pinocchio 自己的双精度结果核过。

STM32G474 @ 170 MHz 上每次调用的周期数。左边是 `update_kinematics` 加上算法，
右边是生成代码的一次调用：

| | | RobotDynamics | 代码生成 | |
|---|---|---|---|---|
| `spine` | `rnea` | **4,843** | 12,498 | **2.6×** |
| 9 dof | `aba` | **10,089** | 27,211 | **2.7×** |
| | `crba` | **4,804** | 11,423 | **2.4×** |
| | `rnea` + `crba` | **7,805** | 23,927 | **3.1×** |
| `xarm7` | `rnea` | **8,312** | 25,354 | **3.1×** |
| 7 dof | `aba` | **21,094** | 30,671 | **1.5×** |
| | `crba` | **9,814** | 24,388 | **2.5×** |
| | `rnea` + `crba` | **15,011** | 49,743 | **3.3×** |
| `go2` | `rnea` | **13,058** | 58,120 | **4.5×** |
| 18 dof | `aba` | **31,526** | 79,780 | **2.5×** |
| | `crba` | **14,104** | 52,920 | **3.8×** |
| | `rnea` + `crba` | **22,419** | 111,042 | **5.0×** |

机器人越大领先越多，因为生成代码的体积跟着模型长，库的体积不跟着长。

体积对比，编译产物的 `.text` 段，同编译器同参数：

| | Cortex-M4 代码 |
|---|---|
| 生成的 `rnea` + `aba` + `crba`，只支持 `spine` | 17,425 字节 |
| …… 只支持 `xarm7` | 29,021 字节 |
| …… 只支持 `go2` | 67,221 字节 |
| …… 三个都要 | 113,667 字节 |
| **RobotDynamics，整个库，任何机器人** | **40,236 字节** |

代码生成慢下来的原因有两个。它会产生成千上万个同时活跃的临时变量，而 Cortex-M4 只有
32 个浮点寄存器，装不下的都得溢出到栈上；再加上代码体积那么大，每次迭代都变成了一次
指令取指。

它是拿体积换算术量。这笔交易在桌面 CPU 上是划算的——同样的对比在 x86-64 主机上，
代码生成赢 1.1–1.7 倍。到了 MCU 上就反过来了。

STM32L413 上的同一组对比在 `benchmark/results/` 里。它的 128 KB flash 只装得下 Go2
一个机器人的生成代码，而 G474 的 512 KB 三个都装得下。

## 测你自己的机器人

`benchmark/` 下每块板子一个移植。以 STM32L413 为例：

```bash
cd benchmark/stm32l4 && make run-bench PLL80=1
```

它会输出一个 CSV，`tools/report.py` 把它变成上面那些表。用 `tools/urdf2c.py` 把你的
模型转进来，它就会出现在测试列表里。
