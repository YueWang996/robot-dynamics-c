## ABA 与 CRBA 的选择

`update_kinematics` 加上各自方法的总耗时，L413 @ 80 MHz：

| 模型 | nv | 基座 | ABA | CRBA | 差距 |
|---|---|---|---|---|---|
| `xarm7` | 7 | 固定 | 257 µs | **198 µs** | CRBA 快 23% |
| `spine` | 9 | 浮动 | **123 µs** | 128 µs | ABA 快 4% |
| `go2` | 18 | 浮动 | **382 µs** | 435 µs | ABA 快 12% |
| `g1` | 35 | 浮动 | **908 µs** | 1704 µs | ABA 快 47% |

同一组测试在 G474 上的结果与此一致到一个百分点以内，说明这是模型的性质而非硬件的。

两个影响因素方向相反：

- CRBA 需要求解 `nv × nv` 方程组，Cholesky 分解代价按 nv³ 增长。浮动基座的六个自由度
  是所有关节的祖先，会使质量矩阵稠密化，没有稀疏性可利用。
- ABA 的关节体惯量同余变换在关节偏置不含旋转时可走快速路径。Go2 的十二个关节和
  spine 的三个关节全部满足；xarm7 的关节偏置为四分之一转，全部不满足。

`spine` 上 4% 的差距在模型变化下可能翻转，建议实测。benchmark 中 `fd_crba` 行与
`aba` 行即此对比。

## 有无 FPU 的差距

在同一块 STM32L413 @ 80 MHz 上测量：把 benchmark 按 Cortex-M3 软浮点编译后运行在
同一硅片上，时钟、flash、源码相同，仅 `-mcpu` 和 `-mfloat-abi` 不同。

| 函数 | 无 FPU 时的倍数 |
|---|---|
| `jacobian_world` | 6–10× |
| `update_kinematics` | 7–12× |
| `crba` | 7–16× |
| `aba` | 12–13× |
| `rnea` | **10–19×** |

倍数与浮点运算密度正相关。flash 增加约 16 KB，RAM 不变。

选型建议：优先选带单精度 FPU 的核，而非更高主频的标量核。80 MHz 的 M4F 比 72 MHz 的
M3 快十倍以上。STM32 系列中 F303 和 G431 与 F103 在价格和封装上接近。

## 代码与内存占用

开启 `--gc-sections`，float32，仅使用 `update_kinematics`、`rnea`、`jacobian`、
`crba`、`gravity`，16 连杆 12 关节：

| 目标 | flash | RAM |
|---|---|---|
| M4F 硬浮点 | 23.5 KB | 6.8 KB |
| Cortex-M3 软浮点 | 39.6 KB | 6.8 KB |
| Cortex-M3，`RD_ENABLE_ABA=0` | 39.6 KB | 5.2 KB |
| Cortex-M0+ 软浮点 | 41.7 KB | 6.8 KB |

整库为 40.2 KB Cortex-M4 代码，上表为链接器丢弃未调用部分后的结果。

Cortex-M0+ 可编译可链接，无 ARMv7-M 或 DSP 指令依赖。**可运行于 STM32F103C8**
（64 KB flash，20 KB RAM）。

按周期数折算到 72 MHz 的 F103，力矩控制频率约为：

| 模型 | 频率 |
|---|---|
| 2 自由度机械臂 | 2.5 kHz |
| `spine` | 1.3 kHz |
| `xarm7` | 650 Hz |
| `go2` | 380 Hz |
| `g1` | 160 Hz |

以上为乐观估计。F103 只有预取缓冲、无指令缓存，而本库是取指受限的。
适用于重力补偿和低速轨迹跟踪，不适用于足式机器人的力矩控制。

## 与代码生成对比

Pinocchio 可对 RNEA、ABA、CRBA 做符号追踪，由 CasADi 为特定机器人生成直线 C 代码：
无循环、无树遍历、公共子表达式全部消除。`benchmark/codegen/` 即对此测试。
双方均为 float32、`-O3`、同一编译器、同一板卡，且都对照 Pinocchio 的双精度结果验证。

STM32G474 @ 170 MHz 单次调用周期数。左列为 `update_kinematics` 加算法，
右列为生成代码的一次调用：

| 模型 | 算法 | RobotDynamics | 代码生成 | 倍数 |
|---|---|---|---|---|
| `spine`<br>9 dof | `rnea` | **4,843** | 12,498 | **2.6×** |
| | `aba` | **10,089** | 27,211 | **2.7×** |
| | `crba` | **4,804** | 11,423 | **2.4×** |
| | `rnea` + `crba` | **7,805** | 23,927 | **3.1×** |
| `xarm7`<br>7 dof | `rnea` | **8,312** | 25,354 | **3.1×** |
| | `aba` | **21,094** | 30,671 | **1.5×** |
| | `crba` | **9,814** | 24,388 | **2.5×** |
| | `rnea` + `crba` | **15,011** | 49,743 | **3.3×** |
| `go2`<br>18 dof | `rnea` | **13,058** | 58,120 | **4.5×** |
| | `aba` | **31,526** | 79,780 | **2.5×** |
| | `crba` | **14,104** | 52,920 | **3.8×** |
| | `rnea` + `crba` | **22,419** | 111,042 | **5.0×** |

模型越大领先越多，因为生成代码的体积随模型增长，本库不随。

编译产物 `.text` 段大小，同编译器同参数：

| | Cortex-M4 代码 |
|---|---|
| 生成的 `rnea` + `aba` + `crba`，仅 `spine` | 17,425 字节 |
| 仅 `xarm7` | 29,021 字节 |
| 仅 `go2` | 67,221 字节 |
| 三个模型全部 | 113,667 字节 |
| **RobotDynamics，整库，任意模型** | **40,236 字节** |

生成代码在 MCU 上变慢的原因有两个：同时活跃的临时变量数以千计，
超出 Cortex-M4 的 32 个浮点寄存器，多余部分溢出到栈；代码体积过大导致每次迭代
都产生指令取指。

同样的对比在 x86-64 主机上结果相反，代码生成快 1.1–1.7 倍。

STM32L413 上的对比数据在 `benchmark/results/`。其 128 KB flash 仅能容纳 Go2 一个模型
的生成代码，G474 的 512 KB 可容纳三个。

## 测量自己的模型

`benchmark/` 下每块板卡一个移植。以 STM32L413 为例：

```bash
cd benchmark/stm32l4 && make run-bench PLL80=1
```

输出 CSV，用 `tools/report.py` 生成表格。用 `tools/urdf2c.py` 转换的模型会自动
加入测试列表。
