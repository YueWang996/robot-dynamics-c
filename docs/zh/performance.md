150 MHz 的 M33 和 170 MHz 的 M4F 在这里的差距主要来自这个。

## 随机器人规模怎么变

STM32G474 @ 170 MHz：

| 机器人 | nv | 力矩周期 | 操作空间 | 正动力学 |
|---|---|---|---|---|
| `spine` | 9，浮动 | 26 µs — 38.0 kHz | 44 µs — 22.8 kHz | 59 µs — 16.9 kHz |
| `xarm7` | 7，固定 | 46 µs — 21.9 kHz | 84 µs — 11.8 kHz | 95 µs — 10.5 kHz |
| `go2` | 18，浮动 | 71 µs — 14.1 kHz | 126 µs — 8.0 kHz | 184 µs — 5.4 kHz |
| `g1` | 35，浮动 | 157 µs — 6.4 kHz | 353 µs — 2.8 kHz | 437 µs — 2.3 kHz |

`g1` 是宇树 G1：29 自由度人形，40 连杆，浮动基座，是这套模型里最大的一个。它在单颗
Cortex-M4F 上闭 6 kHz 的力矩环，在 80 MHz 的 L413 上是 3 kHz，占用不到 64 KB RAM。

## 正动力学选哪个方法

`update_kinematics` + 该方法，在两块 Cortex-M4F 上结果一致到一个百分点 ——
所以这是机器人的性质，不是板子的。

| 机器人 | nv | ABA | CRBA | 赢家 |
|---|---|---|---|---|
| `xarm7` | 7，固定 | 257 µs | **198 µs** | CRBA，−23% |
| `spine` | 9，浮动 | **123 µs** | 128 µs | ABA，−4% |
| `go2` | 18，浮动 | **382 µs** | 435 µs | ABA，−12% |
| `g1` | 35，浮动 | **908 µs** | 1704 µs | ABA，−47% |

（微秒数是 L413 @ 80 MHz。）

有两件事在推这条线，方向相反。Cholesky 求解按 nv³ 增长，没有可跳过的部分，而浮动基座
让它更糟：那六个自由度是所有关节的祖先，质量矩阵没有稀疏性可供分解利用。另一边，
ABA 的关节体惯量同余变换有一条快路径，条件是关节原点不带旋转。Go2 十二个关节全走，
spine 三个全走。xarm7 的原点是四分之一转，一个都走不上，ABA 只能留在通用内核上 ——
这就是为什么 nv=7 的 xarm7 是 CRBA 唯一赢的模型。

spine 在 nv=9 上的 4% 落在换个模型就会翻转的范围内，所以自己测。benchmark 里
`fd_crba` 那行对 `aba` 那行，就是这个比较。

## 选带硬件 FPU 的核

在同一块 STM32L413 @ 80 MHz 上测的：把 benchmark 按 Cortex-M3 软浮点编译，跑在同一块
硅片上 —— 同样的时钟、同样的 flash、同样的源码，只有 `-mcpu` 和 `-mfloat-abi` 不同。

| | 没有 FPU 会慢 |
|---|---|
| `jacobian_world` | 6–10× |
| `update_kinematics` | 7–12× |
| `crba` | 7–16× |
| `aba` | 12–13× |
| `rnea` | **10–19×** |

这个倍数跟着算术密度走，所以 `rnea` 最惨。flash 大约涨 16 KB，是软浮点例程加上更大的
代码；RAM 不变，数据布局跟 FPU 没关系。

结论是选一颗带单精度 FPU 的芯片，而不是选一颗更快的标量核：80 MHz 的 M4F 比 72 MHz
的 M3 快十倍以上。STM32 这边，F303 和 G431 在价格和引脚上都接近 F103。

## 体积，以及跑得动它的最小型号

开 `--gc-sections`，float32，为 `update_kinematics + rnea + jacobian + crba + gravity`
这一组，16 连杆 12 关节：

| | flash | RAM |
|---|---|---|
| M4F 硬浮点 | 23.5 KB | 6.8 KB |
| Cortex-M3 软浮点 | 39.6 KB | 6.8 KB |
| M3，`RD_ENABLE_ABA=0` | 39.6 KB | 5.2 KB |
| M0+ 软浮点 | 41.7 KB | 6.8 KB |

整个库是 40.2 KB 的 Cortex-M4 代码；上表的 23.5 KB 是链接器丢掉该程序没调用的部分之后
剩下的。

Cortex-M0+ 能编译能链接，所以不存在 ARMv7-M 或 DSP 依赖，`RD_USE_CMSIS_DSP` 默认关闭。
**它装得进 STM32F103C8** —— 64 KB flash，20 KB RAM。

折算到 72 MHz 的 F103，力矩周期大约是：2 自由度机械臂 2.5 kHz，spine 1.3 kHz，
xarm7 650 Hz，Go2 380 Hz，G1 160 Hz。这些数偏乐观：F103 只有预取缓冲、没有指令缓存，
而这个库是取指受限的。重力补偿和慢速轨迹可以，腿上的力矩控制不行。

## 对上代码生成

Pinocchio 能把 RNEA、ABA 和 CRBA 符号化追踪，再让 CasADi 为某一个具体机器人吐出直线
C 代码：没有循环，没有遍历，所有公共子表达式都消掉了。那是能找到的最强对手，所以
`benchmark/codegen/` 就是对着它测的。两边都是 float32、`-O3`、同一个编译器、同一块板子，
而且都对照 Pinocchio 自己的双精度答案核过。

STM32G474 @ 170 MHz 上每次调用的周期数，`update_kinematics` 加上算法，对生成代码的
一次调用：

| | | RobotDynamics | 代码生成 | |
|---|---|---|---|---|
| `spine` | `rnea` | **4,843** | 12,498 | **2.6×** |
| 9 dof | `aba` | **10,089** | 27,211 | **2.7×** |
| | `crba` | **4,804** | 11,423 | **2.4×** |
| | `rnea` + `crba` | **7,805** | 23,927 | **3.1×** |
| `xarm7` | `rnea` | **8,312** | 25,354 | **3.1×** |
| 7 dof | `aba` | **21,094** | 30,671 | **1.5×** |
| | `crba` | **9,814** | 24,388 | **2.5×** |
| | `rnea` + `crba` | **15,011** | 49,743 | **3.3×** |
| `go2` | `rnea` | **13,058** | 58,120 | **4.5×** |
| 18 dof | `aba` | **31,526** | 79,780 | **2.5×** |
| | `crba` | **14,104** | 52,920 | **3.8×** |
| | `rnea` + `crba` | **22,419** | 111,042 | **5.0×** |

机器人越大领先越多，因为生成的代码随模型增长，而库不随。

体积，编译产物的 `.text`，同编译器同参数：

| | Cortex-M4 代码 |
|---|---|
| 生成的 `rnea` + `aba` + `crba`，只 `spine` | 17,425 字节 |
| …… 只 `xarm7` | 29,021 字节 |
| …… 只 `go2` | 67,221 字节 |
| …… 三个都要 | 113,667 字节 |
| **RobotDynamics，整库，任意机器人** | **40,236 字节** |

一颗顺序执行、32 个浮点寄存器的核，会把生成代码里成千上万个同时活跃的临时量变成栈访问，
而那个体积让每次迭代都变成一次取指。代码生成是拿体积换算术量，这笔交易在桌面端是划算的：
在 x86-64 主机上它赢 1.1–1.7×。

同样的对比在 STM32L413 上的结果在 `benchmark/results/` 里。它的 128 KB flash 只装得下
Go2 一个机器人的生成代码，而 G474 的 512 KB 三个都装得下。

## 测你自己的

`benchmark/` 下每块板子一个移植。比如 STM32L413：

```bash
cd benchmark/stm32l4 && make run-bench PLL80=1
```

它会写出一个 CSV，`tools/report.py` 把它变成上面那些表。用 `tools/urdf2c.py` 把你自己
的模型带进来，它就会出现在测试里。
