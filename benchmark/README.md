# RobotDynamics benchmark

Measures every algorithm in the library across four robot platforms, on a host
PC, on both CPU architectures of a Raspberry Pi Pico 2 (RP2350), and on an
STM32G474 (see [`stm32g4/`](stm32g4/)).

Raw CSV: [`results/`](results/). Summary tables: the top-level
[README](../README.md).

## Layout

```
bench_main.c        the suite itself -- one file, runs everywhere
bench_platform.h    microsecond clock + arch detection for host / Pico
models/             rd_model_t headers generated from the reference URDFs
results/            captured CSV, one file per architecture
CMakeLists.txt      Pico 2 build (Arm or RISC-V)
```

The models are generated by [`tools/urdf2c.py`](../tools/urdf2c.py) from the
URDFs shipped with [bard](https://github.com/YueWang996/bard-pytorch-dynamics),
so both libraries are benchmarked on identical robots:

```bash
git clone https://github.com/YueWang996/bard-pytorch-dynamics bard
python3 tools/urdf2c.py bard/examples/simple_arm.urdf -n simple_arm -o benchmark/models/model_simple_arm.h
python3 tools/urdf2c.py bard/tests/spine.urdf         -n spine      -o benchmark/models/model_spine.h --floating-base
python3 tools/urdf2c.py bard/examples/example_robots/xarm_description/urdf/xarm7.urdf -n xarm7 -o benchmark/models/model_xarm7.h
python3 tools/urdf2c.py bard/examples/example_robots/go2_description/urdf/go2.urdf    -n go2   -o benchmark/models/model_go2.h --floating-base
```

## Host build

```bash
gcc -O2 -std=c11 -DRD_MAX_LINKS=40 -DRD_MAX_JOINTS=24 \
    -I RobotDynamics -I benchmark \
    benchmark/bench_main.c RobotDynamics/rd_*.c -lm -o bench_host
./bench_host
```

## Pico 2 (RP2350)

### Prerequisites

| Tool | Where from |
|---|---|
| Pico SDK 2.3.0 | `git clone -b 2.3.0 https://github.com/raspberrypi/pico-sdk` then `git submodule update --init lib/tinyusb` |
| Arm toolchain | [Arm GNU Toolchain](https://developer.arm.com/downloads/-/arm-gnu-toolchain-downloads) (`arm-none-eabi-gcc`) |
| RISC-V toolchain | `riscv-toolchain-16-*` from [pico-sdk-tools releases](https://github.com/raspberrypi/pico-sdk-tools/releases) |
| picotool | `brew install picotool`, or build from source |

TinyUSB is required — the board reports its results over USB CDC.

### Build and run

```bash
cd benchmark
export PICO_SDK_PATH=/path/to/pico-sdk

# Arm cores
PICO_TOOLCHAIN_PATH=/path/to/arm-none-eabi \
  cmake -B build-arm -G Ninja -DPICO_PLATFORM=rp2350-arm-s
cmake --build build-arm
python3 ../tools/capture.py build-arm/rd_benchmark.uf2 results/rp2350_arm.csv

# RISC-V cores
PICO_TOOLCHAIN_PATH=/path/to/riscv \
  cmake -B build-riscv -G Ninja -DPICO_PLATFORM=rp2350-riscv
cmake --build build-riscv
python3 ../tools/capture.py build-riscv/rd_benchmark.uf2 results/rp2350_riscv.csv
```

`capture.py` reboots a running board into BOOTSEL, flashes it, waits for the
CDC device to re-enumerate and scrapes the CSV. The board does not need to be
put into BOOTSEL by hand after the first flash.

To regenerate the tables in the top-level README:

```bash
python3 tools/report.py benchmark/results/*.csv
```

## What the harness does

* Auto-calibrates each timing loop to run for at least 50 ms, so the 1 µs timer
  tick never limits resolution.
* Runs the calibrated loop 5 times and keeps the **minimum**, rejecting
  interference from the USB interrupt that services stdio.
* Folds every algorithm's output into a checksum, so nothing gets optimised
  away.
* Seeds joint state from a fixed xorshift32, so both architectures see
  bit-identical inputs.
* Links `copy_to_ram`, so flash XIP cache behaviour and code layout do not
  confound the Arm/RISC-V comparison.
* Primes `rd_state_t` with one `rd_update_kinematics` and then reuses it, which
  is how the library is meant to be driven. `update_kinematics` is timed as its
  own line item.
* Checks each algorithm's status once before timing it, so an early error
  return is never mistaken for a fast algorithm.

The `_heap_probe` row is a **control, not an algorithm**. The library itself no
longer allocates anywhere, so this exercises `malloc`/`free` purely because it
is the only measurement in the suite that touches no floating point at all --
which is what makes it useful when comparing the two architectures. If the
Arm/RISC-V gap were about the core rather than the missing FPU, it would show up
here too. It does not.

An algorithm that returns an error is reported as `unsupported(<code>)` with an
empty timing rather than being measured: `simple_arm`'s URDF has no inertial
data, so `rd_aba` correctly refuses it and timing that error return would be
meaningless.

## Adding a platform

1. Generate a model header with `tools/urdf2c.py` (it enforces the constraints
   the C model has: axis-aligned joint axes, 15-character link names, parents
   declared before children).
2. Add the include and a row to `g_robots[]` in `bench_main.c`.
3. If the model has more than 40 links or more than 32 velocity DOF, raise
   `BENCH_MAX_NODES` / `BENCH_MAX_NV` in `bench_main.c` and `RD_MAX_LINKS` /
   `RD_MAX_JOINTS` in `CMakeLists.txt`.
4. Make sure the URDF actually carries `<inertial>` blocks if you want the
   dynamics rows to mean anything.
